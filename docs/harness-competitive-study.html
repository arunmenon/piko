The Agentic Harness Landscape

A point-in-time framework for comparing terminal coding harnesses, plus a repository-grounded assessment of where piko fits. External market figures are research notes that require revalidation; piko facts are tied to checks available in this repository.

Evidence status. This document mixes two evidence classes. Piko implementation claims marked as local are inspectable in this repository and its test/budget gates. Industry metrics are a dated August 2026 research snapshot: the source index is not a reproducible bibliography, most cells have no direct citation, and none of those external figures are reproduced by piko's test suite. Treat them as reported comparisons to recheck at the original source—not as independently verified results.

01TL;DR

  • Harness design is a material variable. The controlled studies listed below report meaningful outcome and cost differences when the model is held fixed. The exact effect is benchmark-dependent, and this repository has not reproduced it.
  • The reported leaders use different architectures and economics. The snapshot places Claude Code and Codex near each other on one Terminal-Bench version while differing in tool surface, isolation, context strategy, and reported run cost. Recheck the current leaderboard and methodology before citing the values below.
  • Token efficiency is a useful comparison axis, not a standalone result. Fixed prompt size, cache behavior, working-set growth, retries, tool output, model pricing, and completion rate all affect cost per completed task.
  • Provider and protocol neutrality reduce concentration risk. The dated status board records several reported service, licensing, and maintenance changes. Those statuses are time-sensitive and are not monitored by this repository.
  • The lean thesis remains bounded. External studies offer directional support for smaller working sets, while capability benchmarks can reward richer scaffolding. Lean is a cost/inspectability hypothesis, not evidence of universal capability parity.

02Market structure: four layers, four segments

A useful way to map the reported 2026 market is as four layers: models → harnesses → interop protocols such as MCP, AGENTS.md, and ACP → fleet orchestrators that run multiple harnesses. The boundaries overlap, but this decomposition makes ownership, switching cost, and context overhead easier to compare without assuming that models or harnesses are interchangeable.

Harnesses themselves segment four ways:

The structural case for lean: orchestration multiplies per-run context and tool costs, so cost per completed task matters more as concurrency grows. That is a hypothesis to test with end-to-end task artifacts; a small prefix alone does not establish the result.

Reported user complaints (anecdotal, 2026 snapshot)

  • Harness overhead: community threads report substantial fixed prompt and integration overhead. Provider usage at the API boundary is the evidence to collect; an isolated prompt-size screenshot is not a task-cost benchmark.
  • Permission fatigue: users report bypassing repetitive confirmations. That motivates policy-based approvals and stronger isolation, but anecdotes do not establish that prompts are universally ineffective.
  • Compaction trust: users report losing orientation after opaque compaction. Preserving lineage and the pre-compaction transcript improves inspectability, though it does not by itself prove better task outcomes.
  • Doom loops: repeated failing tool calls are a recurring cost complaint. Hard budgets and flail detection bound exposure; their quality/cost trade-off still needs controlled evaluation.
  • Invisible economics: issue reports describe metering, caching, and quality regressions that users detected through their own telemetry. This supports local usage ledgers and versioned artifacts; individual issue claims need direct links and reproduction before being presented as proven.

05What the evidence actually supports

Reported external findings (revalidate before citing)

  • Harness variance: the cited factorial reports that harness choice can change outcomes and even model ranking under controlled conditions. Effect size depends on the harness set, models, tasks, and scoring protocol. Reported source: arXiv 2605.23950; not reproduced here.
  • Harness-Bench: the cited study reports a meaningful spread among harnesses on identical task/model combinations and relates that spread to token use. Reported source: arXiv 2605.27922; not reproduced here.
  • Equal quality can have different economics: Artificial Analysis reports materially different token use and caching behavior among high-scoring stacks. Compare cost per successful task, not token count in isolation. Reported source: artificialanalysis.ai; methodology and current values must be checked.
  • Fixed overhead matters: third-party measurements report large differences in first-turn prompt size and schema overhead. Those measurements are sensitive to version, enabled integrations, model tokenizer, and cache state. Reported sources: Systima and provider documentation; no artifact is stored here.
  • Vendor-internal evidence is directional: a Databricks post reports less context and lower task cost for a lean harness, but does not publish enough per-harness result detail here to support an independent comparison.
  • API-boundary measurement is the right method: third-party snapshots report substantial first-turn and working-set differences. They are examples of methodology, not piko benchmark results.

The caching inversion complicates the lean thesis. Provider prompt caches have model-dependent minimums, lifetimes, and discounts. A prefix can be too small to qualify for caching while a larger stable prefix becomes cheap on later turns. The current thresholds must be checked in provider documentation. Net: fixed-prefix size is a local context-discipline metric; the economically meaningful metric is end-to-end cost per completed task, including cache reads/writes, retries, tool output, and failures.

Claims the original research flagged as non-comparable

  • Large Cursor-vs-Claude-Code or CORE-Bench swings assembled from different boards, versions, or harness configurations. Do not compare them without a shared protocol.
  • "pi tops the Terminal-Bench leaderboard" — the original snapshot found no official pi submission. Recheck the current board before repeating that conclusion.
  • SEO-tier TB scores in the 85–92% range attributed to harnesses — those are Artificial Analysis model rankings under the fixed Terminus 2 reference harness, a different board.
  • Vendor-submitted SWE-bench Verified numbers as model comparisons — 99 of 100 entries ran the vendor's own scaffold; they are model+harness composites.

06Where piko sits

piko (github.com/arunmenon/piko) is a clean-room TypeScript implementation of the lean thesis. The CLI exposes four workspace file tools by default; host bash is a separate, unsandboxed opt-in. Its checked all-built-ins context estimate is roughly 750 tokens on this revision, including the bash schema, and CI-gated below 1,000. It has no third-party runtime packages, records durable JSONL lifecycle state, and compacts into lineage-linked session files. It does not implement in-process sub-agent orchestration.

Honest position: piko demonstrates a coherent lean architecture and locally tested containment, protocol, budget, journal, and telemetry contracts. It does not yet demonstrate industry-level capability or economics. It is pre-1.0, single-maintainer, unaudited, has no OS sandbox, stable compatibility promise, established ecosystem, or published representative cross-harness benchmark. Its present value is as an inspectable experimental framework whose claims can be turned into reproducible evidence.

07Strategic read

  • The lean bet is testable, not settled. External studies give directional support to context discipline, especially when work is fanned out, but piko needs repeated, paired trials to show its own cost/quality position.
  • Capability benchmarks can reward scaffolding. The reported leaders combine model and harness effects, while published ablations attribute some gains to tools, middleware, and memory rather than prompt slimming. The defensible lean pitch is cost, inspectability, and auditability—not "matches capability everywhere."
  • Differentiation may be migrating from integration count toward context discipline, cache engineering, portability, and trust. That is a strategic inference from the snapshot, not a measured market fact.
  • Minimalism alone is an occupied position. Upstream pi already combines a lean core with a reported extension ecosystem, while derivatives explore richer surfaces. Piko therefore needs evidence on adjacent axes—safe execution, reproducible cost per completion, backend composability, or a simpler deployment artifact—rather than prefix-size claims alone.
  • For piko specifically: (1) retain the budget gate and lineage-preserving compaction, but publish cost per completed task with raw, versioned artifacts; (2) evaluate flail-capping with repeated paired trials and report failures as well as successes; (3) keep the repo map, but measure whether it reduces calls or tokens; (4) distinguish the legacy Terminal-Bench adapter from a current Harbor submission; (5) add a real sandbox/approval layer before presenting host execution as production-safe; (6) add protocols such as MCP or ACP only with measured context and trust costs; (7) preserve provider-neutral request and telemetry contracts.

08Comparability cautions from the research snapshot

  • pi is by Mario Zechner (now at Earendil, with Ronacher and Steinberger) — not "by Armin Ronacher."
  • Qwen Code is not "just a Gemini CLI fork" — the maintainers formally stopped syncing at v0.1 and the feature surface has no Gemini CLI equivalent.
  • Terminal-Bench 1.0 scores ("Droid tops at 58.75%") are still quoted as current; the boards are not comparable across versions.
  • Gemini CLI's README still advertises a free tier that stopped serving on 2026-06-18.
  • "Codex is 4× more efficient" conflates tokens with dollars — on TB2.1 Claude Code was 3.7× cheaper at indistinguishable accuracy while plausibly using more tokens.
